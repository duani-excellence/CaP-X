# Graph v2 冻结质量与压力实验审查

本报告是开发期工程审查，不是正式模型效果报告；未发起新 LLM 请求。正式实验仍 NO-GO，需完成当前版本三任务在线验收、固定开发场景、功效与总预算，再冻结。

## 冻结与复跑

- Campaign 保存完整本地 AST 导入闭包及配置明确列出的模型静态资产，逐文件记录 SHA256，`source-bytes/` 保存相同字节。当前开发配置约 320 文件 / 3.15 MB，不含模型权重下载。
- Runner 保留原 `sources/` 结构，补完整源码字节归档。G0/G1 标定单独保存原始 Panda MJCF、mount MJCF、IK URDF 和变换/hash；线上校正仅使用公开静态标定及机器人状态。
- 每组、代码块和请求边界检查来源漂移；campaign 在下一 unit 前再次检查。漂移标为 `source_changed`，保留已执行结果，后续组不发请求、不执行物理动作。
- 开发 gate 计固定场景的真实尝试，包括真实 API 错误与初始代码无效。需要同 Snapshot 初始化、初始私有评价记录、真实请求/响应或失败 receipt、terminal 和完整三组账本；不按程序合法或任务成功选择场景。环境没有初始化、Mock、缺组及未知请求不计已完成开发场景。
- 正式 gate 要求开发/测试 Seed 不交、开发与正式运行源码/提示词/评分一致，模型/服务身份/运行环境/标定资产一致，完整 test Snapshot manifest 和真实任务成功 acceptance。服务启动后源码修改与未知身份 fail closed。
- 场景为 bootstrap 独立簇，两次初始生成不算两个独立场景。分析按任务等权；normal、fault、ablation 分开。缺失配对 hash、缺失 draw、部分场景均显式输出，不能给正式结论；`campaign_status` 给尚未运行的完整场景数。

源码归档与磁盘 hash 仍不能证明长驻 Python 服务内存中每个字节的身份，或冻结远程 DeepSeek 权重。动态导入、已安装依赖的内部代码、外部共享库/完整 mesh 资产尚未实现可搬迁的整环境封装；当前记录版本、明确静态模型来源和实际服务进程。模型 response_model/fingerprint 保留在请求档案。不要把这称为位级全系统可复现。

## 当前压力故障实际含义

| 故障 | 触发点 | 可证明的能力 | 不能据此声称 |
|---|---|---|---|
| support_refresh | 执行 place 前，重新公开感知支撑物并作版本更新 | 旧放置计划失效、依赖诊断、无关证据保留、重验证范围 | 支撑物真的发生物理位移；成功物理纠偏 |
| missing_baseline | 抓持后清掉历史 baseline 变量 | 受控停止重复抬升、公开视觉共动 probe、证据恢复和跨 actor 状态 | 挽救掉落或失败抓持；图本身已提高任务成功率 |
| target_shift | place 的请求位置加 25 mm，执行真实运动 | 公开感知检测误放风险，释放前局部对齐及后续继续执行 | 单靠最终 reward 证明偏移已实际发生；把共同控制/验证器收益归为图 |

`Lift` 没有 place；因此当前通用 `stress.json` 中 Lift 的 support_refresh / target_shift 不会触发。运行时必须按适用任务分别选择；`fault_fired=false` 是未触发，不能计为恢复成功。

现有离线独立标注覆盖 release/control/hold。新感知几何、gripper_sweep、attachment_consistency 等不具备完整独立真值准确性标注；条件性 attachment/support 不能作为独立正确性证据。unknown 与未覆盖检测器需单列。`invalid_recovery_actions` 当前只统计有独立前后风险证据且没有改善的物理修正，并非所有无效 LLM 代码/重复感知的总数。

## 最小真实实验集建议（不是正式测试替代）

先修通当前共同底座的 Stack/Restack 正常执行。之后一次初始生成、G0/G1 共享初始代码与 Snapshot，按任务/故障选用独立输出目录：

1. 正常：三任务各 1 个历史场景 + 1 个新开发场景，B0/G0/G1 共 18 episodes。包括无需恢复的成功例；失败也全部保留。
2. 支撑刷新：Stack 1 历史 + 1 新场景，G0/G1 共 4 episodes。检查旧 place plan 被阻止、无关 grasp/历史基线保持有效，恢复只重做关联后缀。
3. 缺失 baseline：Lift 1 历史 + 1 新场景，G0/G1 共 4 episodes。要求没有第二次盲目 lift，公开 hold probe 与后续任务完成分开统计。
4. 目标偏移：Stack 1 历史 + 1 新场景，G0/G1 共 4 episodes。确认实际物体/TCP 误差、阻止释放、物理误差下降、独立 release 风险清除、最终物理任务成功。局部修正后已存在的 retreat plan 必须失效并重验证；若模型从未提前形成 retreat plan，该 episode 不能证明此机制。

总计 30 episodes，18 次唯一初始请求；恢复请求另计，上限最多再 210 次（8 blocks）。这是小规模机制闭合/开发集，不能替代每任务约 20 场景开发或后续正式场景聚类统计。

G0/G1 相同验证器、拦截点、公开观测、底层控制和预算；图消融分别关闭诊断切片、精确失效或恢复范围，其余一致。分析将“公开证据恢复”“实际物理纠偏”“最终任务成功”分别展示。无需把所有故障应用到每任务。

## 正式预算不能沿用开发默认值

8 blocks 下 B0 最多 8 次请求，G0/G1 共用初始请求后最多 15 次，三组合计每 paired unit 最多 23 次。3 任务 × 20 场景 × 2 初始生成 = 120 units，最坏 2760 请求；正式 600 units 则最多 13800 请求。当前配置 2400 请求 / 604800 秒是开发限制，不足以保证全量完成，需依据冻结开发产物另定正式累计请求、费用与墙钟预算。费用字段是保守上界或 usage 估算，不是账单实付。
