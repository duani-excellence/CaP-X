# Vision Oracle 放置失败诊断（2026-11-19）

**结论：在历史 Seed 21 中，最直接的失败因素是绿色方块的水平定位偏差，与抓持后红方块中心相对 TCP 的偏移相加。不是抓取失败，也没有证据表明主要由末端水平到位误差引起。** 仅把绿色中心 XY 换成真值就恢复成功；只改高度或单个方块尺寸仍失败。尺寸高估和高处释放是同时存在的问题，但不是本例失败的唯一原因。

## 复现条件与限制

复用 `outputs/model_comparison/pilot_20261112_193853` 的 Seed 21/0 初始 Snapshot、原始 Oracle、视觉 API 返回、抓取候选及 Trace。新增两个诊断脚本位于 `capx/experiments/vision_diagnostic*.py`，复用 `pilot.run_trial`、原 Sandbox、控制 API 和物理评分；未修改生产算法、Oracle 源码或成功判据。

本轮环境已变化：原 SAM3 8114、PyRoKi 8116 未在线，NVIDIA 内核驱动 580.173.02 与 NVML 580.178 不匹配。没有停止其他项目服务或修驱动。使用已安装的 Mesa 软件渲染和**原 PyRoKi 求解实现的 CPU 后端**，冻结历史视觉 API 输出后重跑物理过程。因此这是**历史感知输出驱动的物理反事实实验，不是在线 SAM3/GraspNet 全链路重新验收**。

共 10 个有效 Oracle Trial，另保留 1 次未进入仿真的 EGL 初始化失败。LLM 请求 **0**。两个初始物理 hash 与历史完全一致；Seed 21 baseline 各关键 API 后 TCP/红方块位置及仿真时间与历史一致；Seed 0 最大红方块差异 0.000316 mm。部分反事实 CPU IK 输出有 ≤7.61×10⁻⁶ rad 差异，放置前红方块偏差最大 0.123 mm；共同抓取/抬升目标一致。这项数值差异远小于约 12 mm 的定位干预，但仍保留在证据中，不称为逐步完全相同。

## 逐阶段误差

以下距离单位为 mm，位置误差为“估计−真值”。尺寸为机器人基座坐标系完整轴向长度。

| 项目 | Seed 21：失败 | Seed 0：成功 |
|---|---:|---:|
| 初始红块中心误差 XYZ | +9.06, −4.66, +9.20 | +8.25, −3.46, +10.51 |
| 放置前绿色中心误差 XYZ | +11.91, −4.00, +11.55 | +8.54, +7.19, +13.03 |
| 绿色估计高度 / 真值 | 85.92 / 50.00 | 86.25 / 50.00 |
| 红色估计高度 / 真值 | 67.60 / 40.00 | 79.03 / 40.00 |
| 放置目标 TCP（基座 XYZ，mm） | 466.88, 47.54, −8.80 | 682.25, −112.15, −1.44 |
| 实际 TCP−目标 XYZ | −0.46, +0.49, −8.34 | −0.32, −0.06, −8.00 |
| TCP 姿态到位误差 | 0.252° | 0.182° |
| 放置时红块中心−TCP XYZ | +9.77, −0.03, +10.59 | +2.10, +0.49, +13.01 |
| 开始释放时红绿中心 XY 距离 / Z 差 | 21.51 / 90.56 | 12.82 / 100.68 |
| 最终红绿中心 XY 距离 / Z 差 | 48.83 / −5.00 | 14.56 / 44.89 |

正常平放堆叠的红绿中心 Z 差约 45 mm。Seed 21 放置目标高度高了约 43.31 mm，其中绿色中心 Z 偏差贡献 11.55 mm，两个高度半和高估贡献 31.76 mm。

Seed 21 水平误差可直接分解：

`红块−绿块 XY ≈ 绿色定位偏差 [11.91, −4.00] + TCP 跟踪误差 [−0.46, 0.49] + 红块−TCP [9.77, −0.03] = [21.22, −3.53] mm`。

Trace 显示：两例均真实抓持并抬升，未被判为持物阶段滑落。Seed 21 开夹约 0.30 s 后失去双侧抓持，0.40 s 接触绿色方块，此时 XY 偏差约 24 mm；随后偏移增大，约 0.55 s 失去方块间接触，最终回到桌面。Seed 0 在约 0.40 s 接触后保持支撑并稳定。失败发生在释放后的接触/滑离阶段，不是仅凭 reward 推测。

## 坐标、TCP 与剩余假设

- 基座到世界平移为 `[-0.56, 0, 0.922] m`，旋转为单位阵。全部误差已先转换到同一坐标系。
- 从历史 GraspNet 选中候选，经相机外参及局部 `+0.12 m` 变换重算抓取 TCP，与 API 返回的位置差约 10⁻⁸ m、角差 <7×10⁻⁶°。
- 从请求 TCP 经局部 `−0.107 m` 转换到 hand，逐项匹配历史 6 个 IK 请求，最大数值差为 0。未发现本例由 XYZW/WXYZ 混用或坐标重复变换引起的证据。这不能替代真实相机/TCP 标定验收。
- 原 Oracle 定义了竖直 `place_quat`，但实际放置 `goto_pose` 仍传 `pick_quat`；Seed 21 抓取轴偏离竖直约 25.40°。它把“期望红块中心位置”直接用作 TCP 目标，忽略约 10 mm 的抓持中心偏移。全部真值后补偿该偏移，最终 XY 从 16.46 降为 1.53 mm，说明值得后续修正，但该补偿同时改变 XYZ，不能单独归因于某一轴。
- 视觉采用可见点云 OBB 中心，以及旋转 OBB 转为基座 AABB 的外包尺寸。观测到的中心偏移/高度高估与这种估计方式相符；**部分表面可见、分割边缘、OBB 轴倾斜分别贡献多少，尚未确认**，需在线感知恢复后保存 mask/点云再分解。
- 控制存在两例共有的约 −8 mm Z 到位误差；未在本轮消除，不能宣称控制完美。Seed 21 水平误差仅约 0.67 mm，当前证据不支持把主要失败归咎于水平 IK/控制。

## 下一步最小修复建议（本轮未实施）

1. 优先修正绿色支撑块 **XY 中心估计**：在已有 mask/点云上检查可见面造成的中心偏差，采用适合方块几何的中心恢复；不要硬编码本例 −12 mm，也不要将真值带入部署 API。
2. 将放置目标明确为物体目标，再通过抓持后的物体相对 TCP 变换换算 TCP；处理持物姿态，不要仅把 `pick_quat` 改成竖直姿态而忽略持物旋转。
3. 校正完整高度估计与释放间隙。避免几十毫米高的开夹掉落；用独立的新 Seed 检验，保留原评分门槛。
